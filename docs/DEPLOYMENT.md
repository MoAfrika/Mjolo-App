# Netlify + Supabase deployment

No deployment or production publication has been performed by this implementation.

1. Locate the **existing intended staging Supabase project** and confirm its project reference and separation from production. Do not create a replacement or duplicate project. Review its hosting region and current data before making changes. If the only accessible project is production, stop before migrations/Auth changes and request an explicit staging target. See [the staging runbook](STAGING.md).
2. Install Node 24 and the Supabase CLI. From this checkout, use `supabase login`, `supabase link --project-ref YOUR_PROJECT_REF`, then `supabase db push`. Inspect the planned migrations first. The migration creates the private account schema, protected RPCs, RLS policies, private `profile-photos` bucket and Realtime publication. No production seed data is applied.
3. Supabase Auth: enable email confirmations, require passwords of at least 12 characters, enable secure password change and refresh-token rotation/reuse detection. Use an access-token lifetime of 900 seconds. Disable anonymous signup. Keep public signup limited to email/password until other methods are explicitly implemented. The database refuses users without adult and terms consent except the controlled administrator provisioner.
4. Configure a real SMTP provider in **Supabase Auth → Email/SMTP**. Enter the provider's host, port, username, password and verified sender there, not in frontend variables. Enable TLS, verify sender DNS (SPF/DKIM/DMARC), and send a test email. Supabase's default email sandbox is not sufficient for public registrations. Review Auth IP/login/signup/email rate limits for production traffic; local config intentionally permits more verification emails for tests. Enable provider-supported abuse protection after verifying its application integration; CAPTCHA UI is not currently implemented.
5. Locate and link the **existing intended Netlify site** by Project ID. Do not create a new site. Use an isolated staging/branch-deploy context or the confirmed dedicated staging site. Build: `npm run build`; publish directory: `dist`; functions: `netlify/functions`; Node 24. `netlify.toml` supplies routing, security headers and function bundling. Do not change production environment values, expose secrets to untrusted previews, or publish to production.
6. Configure the six deployment variables and the separate one-time administrator secret exactly as listed in [Environment variables and provider settings](ENVIRONMENT.md). That guide specifies where to obtain each value, its Netlify scope, sensitivity and enabled features. The administrator password belongs only in the controlled provisioner process, not the website build or normal function runtime. SMTP credentials belong in Supabase Auth settings. No proxy or Tailscale is required. Never commit or log credentials.

7. In Supabase Auth URL configuration set Site URL to the exact production origin and allow that origin for email verification/recovery redirects. Do not allow arbitrary wildcard preview origins in production. Password recovery uses `/?recovery=1`; the provider's PKCE callback must finish in the browser that requested it. Email verification may require signing in afterwards. If a custom Supabase domain is used, update `connect-src` and `img-src` in Netlify CSP to that exact trusted domain. Current CSP permits standard Supabase project domains only.
8. Run `npm run admin:provision` in a controlled server environment using the confirmed staging URL and service key, with the new password injected securely. Confirm the requested identity, use Resend verification, verify the email, sign in, and complete the mandatory password change. Remove the initial-password variable. The app cannot assign admin via public signup or editable user metadata. For stronger administrator assurance, add and enforce provider MFA before public launch (not yet implemented).
9. Verify the uploaded function is bundled correctly, the private bucket denies anonymous downloads, SMTP delivers and recovery completes, Realtime events arrive only for authorised matches, and two deliberately created adult QA accounts complete the entire journey. Never point the automated local suites at production. Remove QA users and photos after manual hosted validation.
10. Publish only after the operator approves the finished deployment and completes the launch checklist in SECURITY.md. Configure provider backups/PITR, test restoration, monitoring, retention/deletion jobs, reporting staffing, privacy contact and incident response. Supabase plan limits and realtime quotas must match expected load.

Netlify static hosting does not provide PostgreSQL, SMTP, private storage or Realtime. Those services must be connected to the same Supabase project; there is no silent local fallback. `.env.example` contains names and placeholders only. Missing frontend settings show a setup screen; failed requests are surfaced instead of returning invented data.

## Local-only cloud networking workaround

The cloud machine has a read-only home directory and Docker's space-heavy VFS storage driver. The standard CLI's local config directory and the large Supabase database image may require environment-specific preparation. The onboarding evidence records which commands actually worked. Do not disable artifact verification, change expected checksums, or overwrite unrelated Docker state to make setup pass.
