# Netlify + Supabase configuration

The implementation reads **six deployment settings** and **one one-time provisioning secret**. No proxy, Tailscale, VPN, database connection string, or custom networking service is required for the standard public Netlify + Supabase deployment. The browser connects directly to Supabase over HTTPS/WSS; Netlify Functions connect to Supabase over HTTPS.

Use the same Supabase project for all four URL/client-key settings and the privileged key. Obtain values from your own project; the checked-in `.env.example` contains placeholders only. Do not copy the generated local development `.env.local` into a hosted deployment.

The current tested key path is the legacy `anon`/`service_role` pair. Supabase may also offer newer publishable/secret keys; these have not been verified against a hosted project in this implementation. Do not place a privileged `service_role` or secret key in either `ANON_KEY` setting, even if the SDK accepts the string.

`VITE_` values become public during `npm run build`; changing them requires a new reviewed build. Function settings must be available to the deployed function runtime. Keep production secrets out of untrusted deploy previews; use an isolated staging Supabase project and context-specific settings for staging. If your Netlify plan does not offer per-scope controls, use an equivalent server-only secret-management setup and verify the resulting build contains no privileged credentials.

## Supabase dashboard settings, not application environment variables

- **Authentication → Email / SMTP:** obtain SMTP host, TLS port, username, password and verified sender email/name from your email provider. Configure them in Supabase, along with the provider's required SPF/DKIM/DMARC DNS records. The app does not read `SMTP_HOST`, `SMTP_PASSWORD` or other SMTP environment variables. This enables real verification, resend and password-recovery email delivery. Netlify does not send these messages.
- **Authentication → URL Configuration:** set Site URL to the final app origin, and allow the verification/recovery redirect URLs for that origin, including `/?recovery=1`. Avoid unrestricted production preview wildcards. PKCE recovery must finish in the browser that requested it.
- **Authentication settings:** enable email confirmations, minimum 12-character passwords, secure password changes and refresh-token rotation/reuse detection; use a 900-second access-token lifetime and review production rate limits. Local `supabase/config.toml` does not configure a hosted project's Auth settings automatically.
- Apply all SQL migrations using the controlled Supabase CLI workflow. They create tables, access policies, the private `profile-photos` bucket and the Realtime publication. These features do not require extra app environment variables or a database password in Netlify.
- A custom Supabase API domain requires the corresponding HTTPS/WSS hosts in `netlify.toml` CSP and the URL settings above. Standard `PROJECT_REF.supabase.co` domains already match the configured CSP.

The Supabase account access token and database password may be requested by `supabase login`, `link` or `db push`. They are tooling credentials for the controlled migration environment, **not runtime app variables** and not frontend configuration. Do not add them to `.env.example` or the website's public build settings. `NODE_VERSION=24` is already supplied by `netlify.toml`.

## Local development and tests

`npm run db:start` and `node scripts/local-env.mjs` prepare isolated local Supabase settings in ignored files. `LOCAL_TEST_JWT_SECRET` is a local-test signing secret, never a hosted deployment setting or browser variable. `SUPABASE_CLI`, `SUPABASE_INTERNAL_IMAGE_REGISTRY`, `SUPABASE_INTERNAL_JWT_SECRET` and `CHROMIUM_PATH` are optional local tooling/test overrides, not required Netlify + Supabase settings. No Tailscale or proxy environment variables are required by the application.

## What still needs hosted configuration and validation

Local Auth, mail capture, PostgreSQL/RLS, private Storage, Realtime, account functions and the two-account journey were tested against local services. That does not verify an unconnected hosted project. Netlify's `@netlify/zip-it-and-ship-it` 16.3.0 packaged the account function locally for Node 24. The extracted handler imported successfully and returned the expected 405 method guard and 503 missing-configuration response. The archive was checked for accidental `.env`/local-state inclusion and embedded service-role values. These checks do not execute the hosted Netlify/AWS request wrapper or authenticated provider operations.

After values and dashboard settings are supplied, validate:

1. Netlify frontend build/runtime settings, function hosting, exact Origin validation and any custom-domain CSP behavior.
2. Hosted Supabase Auth registration, email verification/resend and password recovery through the real SMTP provider, including DNS, sender reputation and redirects.
3. Hosted migration state, RLS, private bucket behavior, recipient-preference/block restrictions and authorised Realtime delivery.
4. Authenticated photo uploads/deletions, exports and password-confirmed account deletion through the deployed Netlify function.
5. The complete two-account journey and persistence in the hosted environment, plus session expiry, unrelated-user denial and blocking.
6. The requested administrator, using the securely supplied initial password. No hosted administrator has been created; the provisioner was tested with a disposable local account only.
