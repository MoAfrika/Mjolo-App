# Security boundaries and launch review

## Enforced by the implementation

- Supabase Auth hashes passwords, verifies email contact ownership, performs password recovery and rotates provider sessions. PKCE is used by the browser client. Auth tokens stay in browser storage managed by Supabase, never URL query strings generated by the app. Strict CSP, React text rendering and no raw HTML rendering reduce XSS exposure. Browser token storage still makes XSS prevention essential; these are not HttpOnly-cookie sessions.
- `private.accounts` is inaccessible to anon/authenticated roles. Roles, status, birth date and initial-password flags are not public user metadata. A trigger validates adult birth dates and consent at registration. The reserved admin identity is available only via service-side creation. A provider password-hash update clears the initial-password requirement; changing user metadata cannot.
- SQL access checks require a verified, active account without a pending initial password change and a currently existing Auth session. Expired JWTs are rejected by Supabase; deleted sessions are rejected by SQL. Moderator suspension revokes sessions. Unverified users can read their own onboarding state but cannot interact.
- RLS is enabled on every application table. Anonymous access is revoked. Users cannot directly mutate application tables; validated RPCs enforce identity, checks, rate limits and state transitions. Other profiles are returned through narrow discovery/match JSON, excluding birth dates, contact information, roles and private preferences.
- Likes and blocks use transaction-scoped pair locks. Reciprocal likes are required for matching, and the canonical participant pair is unique. Message request IDs make retries idempotent. Date versions reject stale edits; only the recipient can accept, and amendments require fresh acceptance.
- Realtime Postgres subscriptions use SELECT RLS. Messages and dates are restricted to active match participants. Notifications contain no independently accessible conversation channel. Blocking removes the match and cascades messages/dates; unblocking does not restore interaction history. New media requests are denied after a block; already downloaded bytes cannot be recalled from a device.
- Private media is fetched with the current authenticated session, not a long-lived public/signed URL. Only the server role uploads. Recipient age/gender preferences also restrict new direct media and like access, while an existing mutual match preserves previously agreed profile access. The server accepts JPEG/PNG raster signatures, limits bytes/resolution/memory, validates PNG CRCs and rejects interlaced/16-bit PNG, resizes and re-encodes JPEG with no EXIF. SVG, animated formats, WebP/HEIF and external-resource codecs are not accepted. Images are compressed client-side too. There is no malware or explicit-content classifier yet.
- Netlify server operations verify the bearer token with Auth, check account state, require exact Origin, and keep service keys server-side. Deletion requires a password reauthentication; storage is cleaned before provider deletion. No privileged key has a `VITE_` prefix. Account operations never log request bodies, tokens or passwords.
- Database rate limits apply to profile saves, swipes, messages, date operations, reports, blocks and uploads. Auth IP/login/email abuse protection is configured at Supabase and must be reviewed on the hosted project. Failed SQL transactions roll back their writes.
- Export includes own profile/preferences, sent messages, likes, own safety reports, and accessible collaborative plans. Infrastructure backups, provider logs and report retention need a published operator policy. No GPS coordinates, home-location fields, ad tracking or sensitive analytics are implemented.

## Required before public launch

1. Complete an independent security review, provider configuration review and hosted cross-account test. The local suite is evidence for the implementation, not proof that an unconnected production project is secure.
2. Publish operator identity, Information Officer and privacy contact. Finalise lawful processing basis, privacy/terms text, retention, data subject request and appeal procedures, cross-border processing arrangements and processor agreements under POPIA. The bundled public notice explicitly identifies these missing operator details.
3. Decide proportionate age assurance. Current adult eligibility is server-validated date-of-birth and consent, not documentary or third-party age verification. No identity/background badge is claimed. Stronger assurance and fraud controls may be required before launch.
4. Enforce MFA for moderators/administrators, configure leaked-password protection where available, test account takeover recovery and establish moderator staffing, escalation and appeal procedures. The admin dashboard does not itself supply a moderation team.
5. Configure backups/PITR and test restoration, set retention for reports/audit/provider logs/backups, handle media-cleanup retries and define breach/incident response. Account/media deletion spans two services and is not a distributed transaction; a provider failure is surfaced and may need operator reconciliation. Deleted data can remain in backups until expiry.
6. Perform accessibility and low-end-device testing, load/concurrency tests, service quota review, abuse/security penetration testing and legal review. Automated screenshots and axe tests do not substitute for assistive-technology and real-device testing.

## Deferred integrations

No AI, payments, video calls, events, push/SMS reminders, automated emergency monitoring, identity/document verification, end-to-end encryption, or automated content moderation are implemented. Calendar reminders work only after the user imports the generated file; check-in sharing is initiated by the user. Quiet-hour preferences are stored for future notifications, not presented as a connected push service. The application has no silent mock of any integration.
